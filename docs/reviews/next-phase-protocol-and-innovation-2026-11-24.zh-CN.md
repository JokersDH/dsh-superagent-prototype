## 3. 架构问题（在本阶段一起处理）

### 3.1 Codex 版本被锁死在 0.164.0（P0，影响同事试用）

驱动和验收都只对 `codex-cli 0.164.0` 成立。同事电脑上的版本很可能不同，产品会拒绝运行，或者行为没有经过验证。

**要求：**
- 启动时探测已安装 CLI 的版本和协议 schema，和一张"已验证能力矩阵"对比；
- 版本已验证：正常使用；
- 版本未验证但协议兼容：标为"未验证版本"，只开放已经通过零模型协议检查的能力，用户界面上明确提示；
- 协议不兼容：明确拒绝，并告诉用户需要哪个版本。
- 不允许静默降级成 fixture，也不允许把新版本的"能连上"当成"已验证"。

### 3.2 驱动抽象只被一个协议验证过

DriverKit、Profile、审批、steer、plan 模式这些语义目前只有 Codex 一个实现，很可能已经带上了 Codex 特有的假设。第二协议接入的过程，本身就是对这层抽象的验证：遇到表达不了的语义，按 RFC 修改公共契约，**不要在驱动里私自复制一套类型**。

### 3.3 扩线时期留下了没有接入的包

按包名统计 `apps/` 生产代码对各个包的直接引用（只是粗略结果，有的包可能通过其他包间接用到）：

| 包 | 直接引用数 |
| --- | --- |
| `workflows`、`testing`、`policy-preparation`、`catalog` | 0 |
| `routing` | 1（只用了 `sharedAttentionRanker`） |
| `usage-insights`（约 4,400 行）、`project-recipes`、`proposals` | 1 |

**要求：** 主线做一次审计，每个包标为三类之一：默认路径在用、研究/实验保留（本阶段创新会用到的保留）、可以删除。删除要走正常的负责人流程，保留历史；不要为了让测试通过而删除。审计结果写进 ARCHITECTURE.zh-CN.md 的一张表。

### 3.4 文档写法

AGENTS.md 开头又出现了"Desktop0.1.1/source9cb4bb00/build…"这样的压缩段落。规则不变：AGENTS.md 只写当前有效的规则，用完整句子；hash、计数等证据放在 reports 或完成汇总里，AGENTS.md 只放链接。

**协议选择：** 优先 **ACP（Agent Client Protocol）**。原规格 `product-spec/04` 已经规划了 `packages/drivers/acp-v1/`。本机目前装有 `claude`（Claude Code 2.1.331）和 `opencode`（1.18.34）。B 先用**零模型**方式探测哪个 agent 能以 ACP 方式启动、能力表是什么，选定一个，并在交接里写清楚选择理由。不要猜协议细节，要以实际 schema 和握手结果为准。

**冻结清单：**

| # | 验收句子 |
| --- | --- |
| L2-① | 零模型探测报告：选定的 ACP agent、版本、能力表（会话恢复、权限请求、取消、运行中输入等），每项标 advertised/observed |

## 5. 里程碑 05：创新（在 04 关闭后开始，或在 04 线 2 完成后提前开始）

### 5.1 原则

不再采用论文级实验那套做法（预先精确计价、三组对照、盲评）。改为**产品化的创新**：功能默认关闭或只给建议；用户主动开启后，在真实使用中记录预先约定的指标；用硬预算控制开销。结论如实写成"观察到的效果"，不说成"统计证明"。

### 5.2 三个创新点（按优先级）

| 优先级 | 创新点 | 建立在什么上 | 指标 |
| --- | --- | --- | --- |
| **I-1** | **用已有决定回答原生问题**：原生 agent 提问时，如果命中一条范围匹配、仍然有效的 UserDecision，问题中心直接给出建议答案和来源，用户一键确认或修改。权限和认证类问题永远不自动套用 | UserDecision（范围、来源、撤销）、QuestionBroker | 命中率、用户采纳率、被用户改掉的比例、误用（撤销后的决定仍被引用）必须为 0 |
| **I-2** | **跨 agent 复核**：对冻结的候选，用户可以点"让另一个 agent 复核"。复核者用另一种协议、新会话、密封副本，只输出发现，不能写入 humanAcceptance，也不能把机器的 FAIL 改成 PASS | 第二协议（里程碑 04 线 2）、冻结 subject、密封副本、可信完成 gate | 复核发现中被用户认可的数量、误报数量、额外 token 和时间；没有发现不等于证明正确 |
| **I-3** | **审阅批处理与推荐顺序**：多个候选就绪时，推荐审阅顺序，可以一次审完一批 | 注意力排序（已在默认路径）、ReviewTiming | 候选就绪到被接受的等待时间，前后对比 |

**基于证据的路由**本阶段不做：需要两个协议都积累足够的真实交付结果（至少几十个任务）之后才有意义。现在可以先确保 ExecutionOutcome 对两种协议都正确记录。

### 5.3 冻结清单

| # | 验收句子 |
| --- | --- |
| I-① | I-1 实现并默认开启"只给建议"；对至少 3 个真实原生问题记录命中、采纳和修改情况；撤销决定之后确认不再被引用 |
| I-② | I-2 实现为可选按钮；在至少 3 个真实候选上运行跨协议复核（其中至少 1 个是人为注入缺陷的候选），记录发现、误报和成本 |
| I-③ | I-3 实现；用里程碑 04 和 05 的真实任务数据报告等待时间 |
| I-④ | 更新 INNOVATION.zh-CN.md：每个创新点写清楚"做了什么、观察到什么、局限在哪"，不夸大成研究结论；重新计算创新分数 |

**预算：** 最多 **10 次**真实调用（I-1 尽量借用里程碑 04 和其他真实任务里自然出现的问题，不单独花额度；I-2 主要花在复核上）。计数规则同 4.2 节线 2。用户可以在开工前调整这个数字。
