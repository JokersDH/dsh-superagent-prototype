# 架构与创新评审：从"可靠转发器"到"有脑子的分发层"

> 日期：2026-11-10 · 状态：评审意见（非验收、非契约变更） · 读者：主 Agent 与 A–E work agent
>
> 目的：给出对当前自研分发层（"方案 B"super agent）的**现状盘点、架构质疑与改进方向、创新增强建议**，供主线和各 work agent 阅读后决定是否调整路线。
>
> 阅读方式：本文不替代 `product-spec/` 契约与各 WP-16 检查点；冲突时以现有契约/ADR 为准。本文是**方向性输入**，任何落地都要走正常 RFC + 验收。引用的文件路径为行动锚点，agent 可据此定位。
>
> 一句话论点：**现有内核（单 writer + 事务 effects + 可信完成 gate + fenced 恢复）是对的，别动；但分发层目前"没有脑子"，创新赌注压错了地方。把创新重心从最难最远的离线学习（G5），前移并收敛到"证据驱动路由 + 跨 agent 验证"——它们复用你已有的独特资产，现在就能产出可见价值，正好是"不止转发"的那部分。**

## 第一部分：现状盘点（诚实画像）

### 1.1 产品定位（来自 `product-spec/README.md`）

本地优先、以主对话为入口的个人开发助理。用户在一个地方讨论、委托多项目工作、回答各 agent 的问题、修订要求、查看验证后的交付、沉淀明确决定。后台协调器持续工作，关闭网页不停任务。首批接入目标 ZCode / DeepSeek Harness / Codex，CAC 后置。

默认复用本仓 superagent 的 Ticket/Assignment 内核，原生 agent 继续承担模型循环、工具执行、原生会话。我们实现跨运行时的**可靠接线、人工交互、目标版本、验证及经验治理**。

## 第二部分：对现状与架构的质疑 + 改进方向

> 说明：以下质疑针对的是"相对于 super-agent 野心"的 gap，不是说现有选择错了。内核的保守是对的；问题在于智能层和创新层的定位。

### 质疑 1：分发层很薄、很被动——它没有"脑子"

**现象**：看 `AgentDriverV1`（inspect/serve/reconcile）与核心 `Decision`（接单/路由），实际路由是*一个合同 → 一个 Ticket → 一个预先选定的执行器*。首版"一个合同版本对应一个主 Ticket，优先使用该执行器已有的 team/subagent"。

**缺失**：没有能力感知路由、没有成本/延迟调度、没有跨 agent 仲裁、没有目标分解。编排层做的是"可靠地把活递过去"，而不是"聪明地决定这活该谁干、怎么拆、怎么验"。

**这正是"不止转发工具"的核心 gap。**

**改进方向 A — 让 Reasoner 从"只读提案"长成 Router/Planner**：
现在主对话 reasoner 被刻意阉割（只读 + 结构化提案 + 执行走可信入口），安全上对，但等于产品自己的大脑是空的。应自觉扩张其职责：任务刻画 → 执行器选择/排序 → 必要时分解。这是显式 scope 扩张，走 RFC，不是偷加功能。相关锚点：`packages/proposals/`、`packages/context/`。

### 质疑 2："异构编排"的价值尚未被证明，脚手架却已建完

**现象**：已建 Driver / Profile / Catalog / conformance matrix / policy-preparation 一整套异构机器（`packages/catalog/`、`packages/driver-kit/`、`packages/drivers/*`、`packages/policy-preparation/`），但第二个执行器从未真正跑起来。

**风险**：在证明"接第二个 agent 带来差异化价值"之前，兼容性脚手架已经很重，差异化却很薄。这是典型的"先建平台后找价值"。

**改进方向 B — 先证明异构价值，再铺满兼容矩阵**：把"接一个真实第二执行器 + 用它跑通一条**跨 agent 验证**窄链路"提前到整套 conformance 机器完工之前。一条能证明"两个异构 agent 相互制衡产生单 agent 给不了的价值"的窄链路，比一张铺满的矩阵更有说服力。

### 质疑 3：创新赌注压在最难、最远、最不确定的地方

**现象**：创新定位在学习层 I1（反馈含义）/I2（团队联合提问）/I3（跨 harness 迁移），全部走 candidate→testing→shadow→active，每步要独立实验 + 预算 + 预声明门槛，defer 到 G5。

**问题**：学习层是 ROI 最不确定、闭环最长、最难证明因果的一块。把创新主赌注全压这里，意味着**短期没有任何可落地的创新**，且很可能长期也发不出有说服力的收益。

**改进方向（见第三部分）**：创新重心前移到能复用现有资产、现在就能产出可见价值的地方。学习层退回成"未来增量"。

### 质疑 4：可信完成 gate 是优点，但也是吞吐天花板

**现象**：每次交付都要漏斗到"机器检查 + 人工接受"。

**问题**：一个真正并行分发多个 agent 的 super-agent，若每笔交付都必须人工点头，并行度一上来，人的注意力立刻成为瓶颈。现在是二元 gate。

**改进方向 C — 验证分级 + 置信度自动接受**：在可信完成 gate 上加一层分级——检查通过 + 变更风险低 + 历史同类高接受率 → 可撤销地自动接受并留痕；否则升级到人。直接复用 `InterventionRecord`（`06` §4）历史作为风险信号。注意：这**不降低**安全边界（高风险仍人工、FAIL 仍不可绕过），只是把低风险长尾从人的注意力里拿走。

### 质疑 5：继承的"概念最小化"哲学与 super-agent 野心冲突

**现象**：继承 DeepSeek `docs/000-philosophy.md` / `001-domain.md` 的"概念最少、设置最少、不得新增概念"，甚至有 Rejected concepts 表 + 元测试（`tests/cards.spec.ts`、`docs.spec.ts`）锁死。

**问题**：这套哲学对一个聚焦的 GitHub 机器人完美；但**有脑子的 super-agent（规划、分解、跨 agent 仲裁）天然需要新概念**（Router 策略、Ticket DAG、typed 交接物…），现有哲学会把它们判死。你现在骑在两匹反向的马上。

**改进方向**：这是必须**显式拍板**的战略岔路（见第四部分），不能让它继续隐性地两头拉扯。

### 质疑 6：I2"团队外部性"新颖性的 scope 与 writer 模型自相矛盾

**现象**：I2 的新颖性建立在"异步团队总人工成本外部性"上；但单 coordinator / 单 writer / 单进程模型里，"团队"实为*一个用户在一台机器上的 fan-out*。真·多机团队（Redis/Temporal/K8s）被明确 defer。

**问题**：最新颖的部分（真实分布式团队成本）被 defer 的架构**在结构上挡住了**。

**改进方向 D — 诚实收窄 scope**：把 I2 的新颖性收窄为"**单用户多路分发下的注意力调度**"，并把它做实（见第三部分创新 ③），而不是声称解决了分布式团队问题。

## 第三部分：如何增强整体创新性

### 核心洞察

> 你手里有三个别人没有的底层资产：
> 1. **协议中立的可信完成 gate**（能对任意异构 agent 的产出做统一裁决）；
> 2. **全链路 provenance / fenced 事实**（每个动作有身份、可审计、可恢复）；
> 3. **attempt 级物理隔离**（独立 Runner + worktree + 资源屏障，可并行/可投机）。
>
> 真正的创新应该**榨取这三个资产**，而不是去赌最难的离线学习。下面四个方向按推荐优先级排列。

### 创新 ①：证据驱动路由（Evidence-based Routing）—— 最该先做

**它是什么**：不是"项目 → 固定执行器"，而是一个**活的路由策略**。给定任务刻画（类型 / 风险 / 仓库上下文 / 所需能力），用系统**自己测量过的事实**来选执行器：
- 能力来源：Profile conformance 矩阵（`04` §4 已经为每个执行器记录了恢复/steer/提问/取消等的 PASS/FAIL/SKIPPED/NOT_TESTED）；
- reward 来源：`InterventionRecord`（`06` §4，每次人工接受 / 返工 / 覆盖）——即"谁在这类任务上可信完成率高、返工率低"。

**为什么是真创新**：*用系统自己验证过的完成事实当 reward signal 来路由异构 agent*——市面上没人能诚实地做这件事，因为别人没有"可信完成 + provenance"这个底座。这不是 LLM 拍脑袋选，是有审计证据支撑的选择。

**为什么现在就能做**：比离线学习好做得多，且天天产出可见价值；复用现有 `packages/catalog/` + conformance + InterventionRecord，不违反单 writer（路由决策作为核心 Decision 的输入，仍由 Engine 事务落地）。

**落地锚点**：`packages/catalog/src/projection.ts`（能力投影）+ 一份新的路由策略 RFC；路由决定进入核心 `Decision`，不新建第二套状态机。

### 创新 ②：跨 agent 验证 / 竞速执行 —— 最能兑现"异构"二字

**它是什么**：因为完成 gate 协议中立，同一个合同可以：
- **交叉验证**：派给 agent A 实现，用 agent B 独立验证/review A 的 patch，对冲突做仲裁；
- **竞速/投机执行**：attempt 本来就隔离，并行跑两个执行器，保留验证得分最高的那个候选，其余丢弃。

**为什么是真创新**：这是**单个 agent 永远做不到的"分发层独有能力"**——把"异构"从成本（要维护多个 Driver）变成价值（互相制衡、择优交付）。它直接回答了"为什么要有分发层而不是直接用 Codex"。

**为什么现在就能做**：attempt 隔离（独立 Runner + worktree + barrier）和可信完成 gate 都已存在；缺的是"同合同多 attempt 竞速 + 择优"的编排逻辑和时序。

**落地锚点**：`apps/runner/` + `packages/execution/`（并行 attempt）+ `packages/verification/`（把 gate 用作跨 agent 裁判）；需要一份时序 RFC 说明它如何嵌进现有 fenced 恢复，不破坏"不重复 begin、保留不确定状态"的不变量。

### 创新 ③：把"注意力经济学"做成真正的调度优化

**它是什么**：DeepSeek 哲学"占用最少人类注意力"现在只是个 UI 排版原则（`005-panel.md`）。把它升级成一个**跨项目、跨并发任务的注意力调度器**：什么时候打断用户、把多个决策批量成一个还是拆开问、哪个问题此刻问的 ROI 最高、哪些低风险交付走自动接受（接创新 ①的风险信号 + 改进方向 C）。

**为什么是真创新**：这正是 I2 的团队成本模型，但应用在"**一个用户的注意力**"这个你真实拥有、架构上做得到的场景上——而不是声称解决了分布式团队外部性。把 defer 掉的最新颖部分，收窄到一个能落地的 scope。

**落地锚点**：QuestionBroker（`packages/questions/`）的投递排序/批量策略 + 面板投影（`apps/console/`）。

### 创新 ④：provenance 账本本身做成产品——异构 agent 工作的"黑匣子 + 反事实重放台"

**它是什么**：`06` §7 已设计 R0–R3 的重放证据阶梯。把它提前兑现成一个**可查询、可重放、可审计**的异构 agent 工作飞行记录仪——不必等学习闭环跑通，就能作为独立价值（尤其对团队协作/合规/事后复盘）。

**为什么是真创新**：一个诚实、fenced、可恢复、带反事实重放等级的异构 agent 事实账本，本身就稀缺。这是把你"为了学习"建的基础设施，提前变现成独立产品价值。

**落地锚点**：`packages/storage/`（事实账本只读查询投影）+ `packages/knowledge/`。

## 第四部分：需要拍板的战略岔路 + 建议排序

### 4.1 必须显式选择的岔路

你现在骑在两匹反向的马上，这个必须由主 Agent（和用户）显式拍板：

| | 路线甲：克制的最小编排器（现状惯性） | 路线乙：有脑子的 super-agent（当前野心） |
| --- | --- | --- |
| 哲学 | 概念最少、不得新增概念 | 需要 Router / Planner / Ticket DAG 等新概念 |
| 大脑在哪 | 全在原生 agent | 分发层自己有调度/仲裁的脑子 |
| 创新落点 | 离线学习（慢、难、远） | 证据路由 + 跨 agent 验证（近、硬、现在就能做） |
| 主要风险 | 永远是个漂亮的转发器 | 概念膨胀，要重新谈判继承来的哲学 |

**本评审的建议**：选**路线乙**，但**保留内核的保守**——单 writer + 事务 effects + 可信完成 + fenced 恢复这套不动；只在其之上扩张"调度/仲裁/验证"的脑子，并显式更新继承来的概念最小化哲学（允许为编排智能新增有限、受测的新概念）。

### 4.2 建议的重新排序

1. **近期（现在就做，复用现有资产）**：创新 ① 证据驱动路由 + 创新 ② 跨 agent 验证的窄链路 + 改进 C 验证分级。这三者共同把产品从"转发器"变成"有判断力的分发层"，且都不碰内核不变量。
2. **中期**：改进 A（Reasoner → Router/Planner）、改进 B（先证明异构价值再铺矩阵）、创新 ③（注意力调度）。
3. **远期增量（降级，不再是主赌注）**：学习层 I1/I2/I3、创新 ④ 重放台的完整形态、CAC 接入。

### 4.3 给各 agent 的可执行输入（方向性，具体以后续 RFC 为准）

- **主 Agent**：先就 4.1 岔路拍板；若选路线乙，发起两份 RFC——(a) 证据驱动路由（路由决策作为核心 `Decision` 输入，不新建状态机）；(b) 跨 agent 竞速/验证时序（如何嵌进 fenced 恢复，保"不重复 begin"）。更新 `docs/000`/`001` 的概念边界以容纳受控的新编排概念。
- **A（storage/workflows）**：评估事实账本只读查询投影（创新 ④）与 InterventionRecord 持久化/索引（创新 ①的 reward 来源）所需的 append-only 迁移；不引入第二 writer。
- **B（runner/native/testing）**：优先交付**一个真实第二执行器**跑通跨 agent 验证窄链路（改进 B + 创新 ②），而非先铺满 conformance 矩阵；提供并行 attempt 的隔离与资源证明。
- **C（context/proposals/knowledge）**：评估 Reasoner 扩张为 Router/Planner（改进 A）的受限表示——仍只产受校验提案，但提案内容从"改哪里"扩展到"派给谁 / 要不要竞速 / 要不要分解"。
- **D（launcher/distribution/portability）**：不受本评审影响的发行/迁移工作继续；注意并行 attempt 与自动接受会改变本机资源与备份范围，提前预留。
- **E（product-acceptance）**：为创新 ①②和改进 C 预备独立验收口径——路由/竞速/自动接受都必须有"模型离线仍可查/可停/可人工覆盖""不产生假交付或重复 writer""低风险自动接受可撤销留痕"的失败复现，不把 mock 竞速当异构兼容证据。

## 附：本评审不改变的东西（守住的边界）

- 单 coordinator writer + SQLite WAL + 事务性 effects + Outbox 收据：不动。
- 可信完成 gate 的安全语义（FAIL 不可绕过、native end_turn ≠ 交付、人工接受仍是高风险默认）：不动，只加分级。
- fenced 事实恢复不变量（不重复 begin、保留不确定状态、资源屏障）：任何竞速/并行必须证明仍满足。
- 契约单 owner（主线）、迁移单 owner（A）、root lock 单 owner：不动。
- 诚实报告原则（PASS/FAIL/SKIPPED/NOT_TESTED 分列、不报虚构百分比）：本评审的所有创新主张同样适用——落地前都是"未证明"。
