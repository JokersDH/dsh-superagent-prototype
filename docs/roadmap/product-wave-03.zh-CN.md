## 产品形态与设计方向

网页先作为完整产品运行，界面采用精密工作台：石墨色导航、白色主对话、青绿强调、紧凑而清楚的状态与层级。重点是工作内容、决定与交付，避免营销首页、大型装饰卡片、假指标和不可用的伪控制。未来独立 app 复用同一 React 界面和确定性 API，不把业务逻辑写入桌面壳。

主对话始终保留；项目选择控制上下文，普通发送用于讨论，结构化委托/修订/决定必须有明确确认。侧边显示任务、原生问题和证据，深入时查看完整 diff、实际检查和可操作诊断。界面只消费服务端事实及可用动作，不创建第二个 Work 生命周期。

## 先冻结的消费约定

1. 主线提供公共 DTO/命令和 HTTP fixtures；A/C/D 先提交包内 RFC 说明所需语义，再消费单一 contracts 来源，不能复制私有 wire 类型。
2. A 提供仓储/迁移检查点与只读索引；C/D 通过公开 port 消费，不私建 SQLite writer、不直写生产 SQL。迁移保持 append-only，旧数据和回滚边界有证据。
3. B 的准备、控制、原生问题与资源观察具有完整 attempt/epoch/contract 身份；主线只做确定性组合，不能用 UI 状态或普通文本当停止/完成权限。
4. C 的项目上下文包含授权范围、来源和内容身份；模型输出只产生受校验提案，执行仍经主线命令和当前合同检查。
5. D 的迁移先确认范围和可恢复状态，打包 DB、引用产物及必要私有配置的清单；不复制账号 home/native session、运行 socket 或把旧机器签名/进程身份当新机器权限。
6. E 消费已提交检查点的公共入口，区分实现缺陷、测试工具缺陷和环境不满足；不能修改期望使失败变绿。

## 检查点与持续工作

每人先提交一个稳定 interface/最小纵向检查点，随后连续完成自己的五个阶段。阶段边界消费新 main，代码运行中不切基线。跨模块缺口写明输入、预期/实际、最小复现、需要的公共语义和可继续项；继续 fixtures、负例、独立消费、文档及工具，不逐项等用户批准。

真实任务预算分账：主线本 UI/规划轮 0；A/C/D 0 原生任务；B 新功能包在用户下发后最多 4 个显式小型原生任务，历史账本保留，未知发送不换 ID 重跑；E 默认 0，后续只有显式下发单独预算时才考虑最多 1 个有界发布复验。受控任务和 SDK mock 必须本机隔离，不调用实际模型来填充 UI。

最终报告包括 commit/base、拥有路径、命令和证据、真实已测/未测范围、缺口归属与下一消费者操作。全部队列完成或只剩不能独立消除的阻断时结束；不靠无限轮询或重复模型请求维持“持续运行”。
