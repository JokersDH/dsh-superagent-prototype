# 持续执行队列：用户离开期间的三人分工

日期：2026-11-09。用户要求扩大任务量，允许在现有授权和职责内连续开发。本文件扩展本轮 A/B/main 任务；原任务中的“最终交付”现在是首个稳定检查点，不是整轮停工点。没有经过实测的项目仍是待办，下面不是完成记录。

## 执行规则

1. A 按 A1 → A6、B 按 B1 → B6、主线按 M1 → M6 推进。P0 是可用 MVP 的必需出口；先稳定 P0，再推进 P1，最后做隔离的 P2 增量。P2 不推迟已通过范围的交付。
2. 每个阶段使用拥有路径提交、push 自己分支，发布可消费的检查点后立即继续，不以“等待用户确认”结束整包。主线复验后分段集成；A/B 不 push main，不改彼此 checkout。
3. 跨模块遇阻：把准确输入、预期/实际、最小复现、所需 API 和可继续事项写入自有 `reports/blockers.md`，转做下面列出的独立任务。不能用新私有协议、假 ready 或降低断言绕过阻断。
4. 只在阶段边界、需要消费明确的新接口时 fetch/合并 main；不要在安装/测试/原生任务运行中换基线。产品共享路径冲突保留已验收 main；root lock 冲突使用 main 的结果，新增依赖只交请求，由主线生成权威锁。
5. 保留一个包内进度文件：A 用 `packages/environment-preparation/reports/execution-status.json`，B 用 `tests/native-acceptance/reports/execution-status.json`。记录 phase、pending/running/passed/blocked、commit/base、实际命令、证据、阻断归属和下一项；主线只把已提交结果作为集成候选。不要把运行数据库或日志原文塞进进度文件。
6. 用户不在时，不自动替用户批准真实项目操作。测试可以回答自己隔离实例内、已授权无害动作的问题。真正用户问题保留 pending，agent 继续不依赖该答案的工作。
7. 模型预算不因队列变长而自动增加：B 本轮最多 4 个原生模型任务（包括此前已开始的）；主线本扩展轮最多 2 个私有临时项目任务。按 attempt/begin 记账，不把“API 请求数”当模型任务数；不确定受理先核对同 commandId。额度耗尽后继续无模型工作，不等候或偷换账号。A 不运行模型。
8. 全部队列完成或只剩不可消除阻断时，提交最终交接后结束。不要为了保持运行制造无关功能、无限重试、轮询或空转；没有新的代码/失败/基线变化就不重复付费或宽泛回归。

## 遇阻时的工作选择

- A 等待根依赖锁或 Runner 接线：继续 inspect、离线 fixtures、独立进程消费样例、凭证攻击/恢复与性能测量；使用已有 process port 的受控实现，不去改 Runner。
- B 等待主线故障修复：先提交该失败用例，继续其他故障、浏览器、conformance 和无模型稳定性测试。环境未接入先验无依赖项目，不把整个 native 分支搁置。
- B 无法触发真实权限问题或模型额度用完：保留精确 NOT_TESTED，继续受控问题全链路与公共契约验证；不编造 native 事件。
- 主线等待 A 的稳定 API：推进 WorkspaceManager 的可信附加接口、已有 API 的工作台错误状态、doctor 和 B 的独立故障复现。真实安装保持关闭；不复制一个临时环境实现。

## 联调与收尾

主线只读消费 A/B 已提交的接口和证据；普通文件交接不要求用户转述每个缺陷。A/B 每阶段报告明确“主线下一步”和可独立继续项。集成修复发到 main 后，相关 agent 在安全阶段边界消费，再只复验受影响的范围。

最终用户出口保持具体：导入干净的单包真实依赖项目，看到准确环境状态，明确委托给 Codex，在独立 worktree 改代码，看到检查、完整 patch 和实际停止/恢复结果，接受当前交付后重开仍保留。P2 workspace/新执行器工具必须独立标注支持范围，不自动升级默认产品能力或完整 G2。
